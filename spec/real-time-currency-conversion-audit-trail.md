**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** This feature should be implemented inside `src/backend/Program.cs` and kept runnable through `src/backend/OuterloopLabApi.sln`. Add backend feature files at `src/backend/Features/CurrencyConversion/ConvertCurrencyRequest.cs`, `src/backend/Features/CurrencyConversion/ConversionAuditRecord.cs`, `src/backend/Features/CurrencyConversion/CurrencyProviderClient.cs`, `src/backend/Features/CurrencyConversion/CurrencyProviderResponseAdapter.cs`, `src/backend/Features/CurrencyConversion/ConversionAuditRepository.cs`, and `src/backend/Features/CurrencyConversion/CurrencyConversionEndpoints.cs`. Add at least one backend test at `src/backend/OuterloopLabApi.Tests/CurrencyProviderResponseAdapterTests.cs` and include that test project in `src/backend/OuterloopLabApi.sln`. On the frontend, keep runtime API configuration anchored in `src/frontend/index.html`, and add or update `src/frontend/src/api/currencyApi.js`, `src/frontend/src/components/CurrencyConversionForm.jsx`, `src/frontend/src/components/ConversionAuditLookup.jsx`, and `src/frontend/src/App.jsx` to expose the conversion flow and audit lookup flow.

**In Scope:**
- Add a backend `POST /api/conversions` endpoint that accepts an amount, source currency, and target currency, calls the configured external rate provider, calculates the converted amount, writes a Cosmos DB audit record, and returns the persisted audit details including a generated conversion identifier.
- Add a backend `GET /api/conversions/{conversionId}` endpoint that performs a Cosmos point read and returns the exact previously stored audit record for that conversion.
- Provision and verify the Cosmos database/container during `src/backend/Program.cs` startup using the Managed Identity flow and environment variables already mandated in Known Constraints, then register the repository/services required for this feature.
- Add a provider response adapter that can extract the effective rate and provider date marker from more than one upstream JSON shape without leaking raw provider schema assumptions into the rest of the application.
- Add a React form in `src/frontend/src/components/CurrencyConversionForm.jsx` for immediate conversion and a lookup view in `src/frontend/src/components/ConversionAuditLookup.jsx` for retrieving a past conversion by identifier.
- Display the returned conversion identifier, applied rate, provider date marker, backend execution timestamp, and converted amount in the frontend so an operator can both act now and satisfy a later audit request.

**Out of Scope:**
- Historical-rate queries for arbitrary past dates beyond the current provider response used at execution time.
- Bulk or file-based currency conversions.
- Scheduled refresh, caching, or offline replay of exchange-rate data.
- Exporting audit records to PDF, CSV, email, or external compliance systems.
- User authentication, tenant isolation, or role-based authorization changes outside the existing application baseline.

**Feature Constraints:**
- Use `IHttpClientFactory` for the external currency provider integration, with an explicit timeout and a feature-specific typed client or named client in `src/backend/Program.cs`.
- Keep the provider adapter isolated in `src/backend/Features/CurrencyConversion/CurrencyProviderResponseAdapter.cs`; it must successfully read either `rates.{TARGET}` or `conversion_rates.{TARGET}` style payloads and expose a single internal result model to the rest of the feature.
- Generate the audit record's execution timestamp on the backend with UTC precision using `DateTimeOffset.UtcNow`; persist it exactly as generated and return it unchanged to the frontend.
- Store each audit document with the same `conversionId` value as both the document `id` and the partition key value so `GET /api/conversions/{conversionId}` can use a deterministic Cosmos point read.
- Persist, at minimum, `conversionId`, `sourceCurrency`, `targetCurrency`, `originalAmount`, `appliedRate`, `convertedAmount`, `providerDateMarker`, and `executedAtUtc`; do not persist raw upstream payload blobs unless they are first reduced to the minimal fields required for audit reconstruction.
- Use `decimal` for monetary amounts and rates in backend domain logic; preserve `appliedRate` to at least 6 decimal places and `convertedAmount` to at least 4 decimal places in the stored audit record.
- If the external provider call fails, times out, or returns a payload from which a rate cannot be extracted, return an RFC 7807 `ProblemDetails` response with HTTP 503 and a stable title such as `Currency provider unavailable`; do not write a partial audit record for failed conversions.
- Add automated coverage that proves the response adapter handles both supported upstream JSON shapes and that unsupported payloads fail with the feature's domain exception instead of a raw serialization exception.

**Expected Outcome:** When a user submits `POST /api/conversions` with sample input `{ "amount": 100.00, "sourceCurrency": "USD", "targetCurrency": "EUR" }` and the provider adapter resolves an `appliedRate` of `0.920000`, plus a provider date marker of `2026-08-01`, the API returns HTTP 200 with a payload containing a non-empty `conversionId`, `originalAmount: 100.00`, `appliedRate: 0.920000`, `convertedAmount: 92.0000`, `sourceCurrency: "USD"`, `targetCurrency: "EUR"`, `providerDateMarker: "2026-08-01"`, and an ISO 8601 UTC `executedAtUtc` timestamp including fractional seconds (for example `2026-08-01T10:15:30.1234567Z`). A subsequent `GET /api/conversions/{conversionId}` returns the same persisted values from Cosmos DB without recalculating the conversion. In the React UI, the user can complete a conversion, immediately see the converted amount and conversion identifier, then paste that identifier into the audit lookup view and retrieve the exact same rate and timestamp fields. If the provider is unavailable or returns an unusable payload, the API returns HTTP 503 `ProblemDetails` with the chosen stable title and no new audit document is created.
